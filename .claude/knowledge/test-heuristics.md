# 本产品测试启发式

> 最后更新：2026-06-25
> 来源：13 份历史PRD测试点设计模式蒸馏，适用于知末产品。

---

## 付费流程必查四项（每个支付场景都要过一遍）

```
资损 → 防重 → 一致性 → 降级
```

| 项目 | 问自己 |
|---|---|
| 资损 | 有没有可能多扣/少扣？金额链路三点（详情页/弹窗/实际扣减）是否一致？ |
| 防重 | 快速连击/网络重试会不会重复扣费？有无幂等保障？ |
| 一致性 | 展示、计算、落库三个环节数据是否完全对齐？ |
| 降级 | 服务异常时（网络断/后端挂）用户会看到什么？会不会扣钱但没结果？ |

## 多维度规则的组合覆盖方法

**判定表 + 等价类划分**（适用：会员等级 × 时段、VIP身份 × 有无券、实验组 × 满足条件）

- 建立完整笛卡尔组合矩阵，逐行验证；重点关注容易混淆的相邻格（如黄金高峰 vs 平峰）
- 身份判定四组合（涉及VIP特权时必须覆盖）：
  ```
  VIP+有券 / VIP+无券 / 非VIP+有券 / 非VIP+无券
  ```

**边界值 + 等价类相互验证**

- 不单独依赖某一类方法：额度/时间/版本号临界值需两侧各取一个值验证
- 必问：`>` 还是 `>=`（超过N次触发 vs 达到N次触发）

---

## 时间/状态类场景建模

**状态转换 + 时间轴建模**（跨天/跨周期规则）

- 适用：VIP续费切新价、月度软上限重置、弹窗生命周期、下载额度次日重置
- 构造三类场景：当天到期、跨月第一次、已超限后新月第一次
- 时区/跨日精度确认：自然日 0 点重置 vs 用户操作时刻

---

## AB实验必查三项

```
分组稳定性 → 实验对照隔离 → 埋点不污染
```

| 项目 | 问自己 |
|---|---|
| 分组稳定 | 同账号跨天、VIP状态变化后分组是否不变？多端是否一致？ |
| 对照隔离 | 对照组是否真的保持线上现状，未被实验改造误伤？ |
| 埋点不污染 | 实验改动是否影响了原有GIO埋点？切量写库是否有去重？ |

---

## 异常/负向用例的系统性覆盖

对每个功能点设置"不应发生但易发生"的反面场景，建立反向清单：

- 无券时：不应展示选券字段，但易残留 UI
- 已过期券：不参与计算，但易被误选
- VIP过期：不应享受立减，但易残留展示
- 异常恢复：网络中断/弹窗异常关闭后，状态是否完全复原（无脏缓存残留）

## 存量数据影响分析

需求上线后，主动问：

1. **存量数据（已有券/已有权益/已有记录）**在新逻辑下行为是否正确？
2. **只改了展示但没改计算**，或**只改了计算但没改展示**的不一致？
3. 这个改动会不会影响另一个还在跑的AB实验？
4. 边界用户（B1/B2 维持现状类）是否被新逻辑误伤？

## 覆盖度双维度检查

| 维度 | 检查方式 |
|---|---|
| 功能点维度 | 所有需求点是否都有对应用例？ |
| 属性维度 | 正向/反向/边界/异常/流程各占比是否合理？ |

参考目标：P0 全覆盖，P1 ≥80%，P2 ≥60%；用例总数约为功能点数 × 4–6。

---

## 跨子域测试启发式

遇到涉及多子站的需求，主动问：

- 登录态在各子站是否独立验证？（su需额外UI登录，ai.znzmo.cn需独立登录）
- 功能在哪个子站触发、数据在哪个子站落库？
- AB切量在每个子站是否都正确生效？

---

## 澄清建议系统性应用

每轮测试启动前，收集所有模糊点输出「澄清矩阵」，优先对齐以下：

- 边界值精确定义（`>` 还是 `>=`；起始/截止时刻含不含当天）
- 时间轴重置规则（自然月 vs 权益周期）
- 异常降级策略（服务故障时默认走哪条路）
- 多端/多版本兼容预期

**不在澄清完成前启动用例设计，避免推翻重做。**

## 三分类缺陷打标（发现问题时）

| 分类 | 处置 |
|---|---|
| 研发缺陷 | 功能行为与PRD/用例期望不符 → 规则8反馈，阻断继续生成 |
| 需登录/接口桩 | 缺少前置态导致断言无法执行 → 标 `pending/skip(needs_auth)` |
| 规则9非web | 客户端/后端/渲染计费 → 不纳入自动化，登记CONVERSION-REPORT |
