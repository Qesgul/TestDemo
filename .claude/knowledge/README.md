## 使用约定（test-design 必读）

1. **生成前置**：接到需求后，先 Read 本 README 索引，再按需求域 Read 1–2 张相关知识卡（不必全读）。
2. **few-shot 检索**：用 Glob 列出 `D:\code\testcase\**\test-points.md`，找最相近的 1–2 个历史需求，Read 其 `test-points.md` 作参照，提炼模块划分风格。
3. **生成后回写**：若生成过程中发现新的产品规则/缺陷模式，提交时一并更新对应知识卡（1-2 行追加即可）。

## 维护飞轮（如何确认新知识 + 及时更新）

知识库的价值取决于**是否持续更新**。卡片不是真理，是上次的快照——越用越准，靠的是下面这套机制。

### 一、4 个捕获时刻 → 钩子

| 时刻 | 谁先察觉 | 动作 |
|---|---|---|
| **A. 用户在对话里口述/确认规则** | 主 agent | 最高置信度，当场识别 → 确认归属哪张卡 → 即写 |
| **B. test-design 的澄清矩阵被产品/开发确认** | test-design | 对**跨需求通用**的确认项打标「建议沉淀」，随产物返回，主 agent 决策入库 |
| **C. 同类缺陷反复出现** | test-runner / selector-debug | 单次缺陷走**规则8反馈用户**（不入库）；主 agent 对照 `recurring-risks`，命中**第2次**才升级入库 |
| **D. 会话复盘（兜底网）** | session-recap | 复盘时扫"本会话有无新产品知识漏收口"，统一提议更新哪几张卡 |

A/B/C 即时捕获，D 防遗漏。不靠人记得提醒，靠在这些节点**主动自问**。

### 二、入库门槛——三问（过不了不入库，防噪音 / 防与PRD重复）

1. **跨需求复用吗？** 下个不同需求还会用到 → 入；本需求特有数值/逻辑 → 留PRD，不入
2. **是机制还是会变的数字？** 术语/口径/机制 → 入；具体价格/比例/阈值 → **不入**（**计价明细永不入库**，防过时）
3. **缺陷复发≥2次了吗？** 单次 → 反馈用户；第2次命中同模式 → 入 `recurring-risks`

### 三、置信度分级（决定要不要等用户确认）

- **高**（用户口述 / 产品已确认）→ 直接写，用户口述本身即确认
- **中**（test-design 从PRD推断的疑似通用规则）→ 标 `[待确认]` 写入，下次用到时验证
- **低**（调试中的观察）→ 先不写，复现后再升级

### 四、防过时（纠错路径，比新增更重要）

> test-design 读卡时若发现 **PRD 与卡片矛盾** → **信 PRD**，同时标记该卡条目「疑似过时」回主 agent 提议修正。

### 五、写入通道

- `troubleshooter` capture 回写 `.claude/knowledge/` + **去重**（防膨胀），是登记的维护者。
- 高置信即时场景，主 agent 直接写（知识卡不在规则5测试文档例外，默认需用户确认；但**用户当场口述的规则**视为已确认，可即写）。
